## 🏗️ 3. 전체 파이프라인 학습 (Training Pipeline)
원본 데이터에서 검색 인덱스와 추천 모델을 생성하는 과정입니다. 순서대로 실행하세요.

| 단계 | 실행 파일 | 설명 | 주요 목표 지표 |
| :--- | :--- | :--- | :--- |
| **Phase 1** | `phase1_embedding.py` | CLIP 모델을 이용한 이미지/텍스트 벡터화 | $MRR \ge 0.55$ |
| **Phase 2** | `phase2_two_tower.py` | 후보 추출을 위한 Two-Tower 모델 학습 | $Recall@300 \ge 0.30$ |
| **Phase 3** | `phase2_deepfm.py` | 정교한 랭킹을 위한 DeepFM 모델 학습 | $AUC \ge 0.70$ |

> **💡 Note**: 각 단계가 완료되면 `data/indices/`와 `data/models/` 폴더에 파일이 생성됩니다. 이 파일들이 있어야 시스템이 돌아갑니다.

# 🧪 A/B 테스트 진행 매뉴얼 (A/B Testing Guide)

---

## 🏃 단계별 진행 방법

### 1단계: 베이스라인 데이터 생성 (Control Group)
먼저 일반적인 상황에서의 기본 전환율 데이터를 수집합니다.

1.  `config.yaml` 파일의 페르소나 비율을 **정상 분포**로 설정합니다.
    # config.yaml
    persona_ratios:
      "트렌드세터": 0.15
      "실용주의자": 0.25
      "가성비추구": 0.25
      "브랜드충성": 0.15
      "충동구매":   0.10
      "신중탐색":   0.10
    ```
2.  시뮬레이터를 가동하여 행동 로그(`new_train_logs.csv`)를 쌓습니다.
3.  **CT(Continuous Training) 파이프라인**에 의해 재학습이 완료되면, 이때의 **CVR(전환율)**을 기록합니다. 이 수치가 **A그룹(대조군)**의 기준점이 됩니다.

---

### 2단계: 트렌드 주입 및 모델 최적화 (Experimental Group)
특정 트렌드가 발생했을 때 모델이 이를 얼마나 잘 학습하고 대응하는지 확인합니다.

1.  `config.yaml`을 수정하여 **특정 페르소나(예: 트렌드세터)의 비중을 대폭 상향**합니다.
    # config.yaml 수정 (Jeans 품목 유행 가정)
    persona_ratios:
      "트렌드세터": 0.80  # 트렌드세터 비중 급증
      "실용주의자": 0.04
      "가성비추구": 0.04
      "브랜드충성": 0.04
      "충동구매":   0.04
      "신중탐색":   0.04
    ```
3.  시뮬레이터를 다시 돌리면 트렌드 아이템에 대한 구매 로그가 폭발적으로 증가합니다.
4.  시스템이 이를 감지하여 **DeepFM 모델을 재학습**하면, 최신 트렌드가 반영된 추천 결과가 생성되며 CVR이 변화합니다. 이 결과가 **B그룹(실험군)**의 데이터가 됩니다.

---

### 3단계: 대시보드를 통한 통계적 유의성 검정
수집된 데이터를 바탕으로 대시보드(`http://localhost:8501`)의 **[Tab 3: A/B 테스트]** 메뉴에서 결과를 분석합니다.

*   **A그룹 전환율**: 1단계에서 기록한 기본 CVR (예: 3.2%)
*   **B그룹 전환율**: 2단계에서 기록한 트렌드 반영 CVR (예: 5.8%)
*   **분석 실행**: 두 값을 입력하고 검정 버튼을 클릭합니다.

> **💡 최종 결론 도출**
> 결과 화면에서 **p-value < 0.05**가 확인되면, "DeepFM 재학습이 통계적으로 유의미하게 전환율을 상승시켰음"이 증명됩니다.

### ✅ 1. 구현 완료된 주요 요구사항

**1) 시스템 인프라 및 배포**
*   **Docker Compose 기반 통합 환경**: `docker-compose up --build` 명령어를 통해 API 서버, 대시보드, 시뮬레이터, Redis 컨테이너가 정상적으로 동시에 실행되도록 구축했습니다.

**2) 시뮬레이터 세부 요구사항**
*   **규모 충족 여부 검증**: 상품 5만 건 이상, 고객 1만 명 이상, 행동 로그 100만 건 이상이 정상적으로 생성됩니다.

**3) 멀티모달 검색 및 추천 API**
*   **CLIP + FAISS 검색 API**: 텍스트, 이미지, 하이브리드 검색이 가능하도록 CLIP 모델을 이용해 임베딩하고 FAISS 인덱스로 구축했습니다.
*   **Multi-Stage 추천 로직**: Two-Tower(Candidate Generation), DeepFM(Ranking), MAB(Re-ranking) 알고리즘 파이프라인을 구축했습니다.
*   **API 명세 준수**: 검색 및 추천 API 엔드포인트(`http://localhost:8000/docs`)를 구축하고, 응답 결과에 필수 필드를 포함하도록 설계했습니다.
*   **Feature Store 적용**: Redis를 활용하여 실시간 피처 조회가 가능하도록 서빙 시스템을 구축했습니다.

**4) 대시보드 및 A/B 테스트**
*   **대시보드 운영**: Streamlit 기반 대시보드(`http://localhost:8501`)를 구동하는 데 성공했습니다.
*   **A/B 테스트 시뮬레이션 및 검정 로직**: `config.yaml`을 수정하여 페르소나 비율을 조작하고, 이에 따른 CVR 변화를 대시보드에서 p-value 기반으로 통계적 유의성을 검정하는 프로세스를 정립했습니다.

**5) Continuous Training (CT) 파이프라인 로직**

    *   성능 지표(HitRate, CTR) 주기적 모니터링 가능
    *   신규 로그 1만 건 도달 시 재학습 자동 트리거
---

### ⚠️ 2. 미구현 또는 보완이 필요한 요구사항


**1) 정량적 성능 지표 (핵심 보완 대상)**
*   명세서에서는 각 모형의 최소 성능 기준을 요구하고 있으나, 현재 일부 지표가 이에 미치지 못하는 상태입니다.
    *   **검색 성능**: MRR ≥ 0.55, NDCG@10 ≥ 0.50(성공)
    *   **후보 추출 (Two-Tower)**: Recall@300 ≥ 0.30(실패..)
    *   **랭킹 (DeepFM)**: AUC ≥ 0.70(실패..)
    *   **추천 전체 성능**: HitRate@50 ≥ 0.20, NDCG@50 ≥ 0.08, Coverage ≥ 0.20(실패..)
    *   **응답 속도**: 검색 및 추천 API 각각 200ms 이내, Redis 피처 조회 10ms 이내 달성 여부 확인 필요(성공))


**2) Re-ranking 비즈니스 로직**
*   해당 부분은 잊고 못했습니다.......
    *   동일 카테고리 상품 연속 3개 이상 노출 금지 (다양성 조절)
    *   행동 이력이 5개 미만인 신규 사용자(Cold Start)에게 인기/트렌딩 상품 추천
    *   등록 7일 이내의 신규 상품에 대한 노출 기회 보장 로직


**3) 문서화 (`docs/` 폴더)**
*   평가 프로토콜에 맞춘 **실험 결과 리포트**를 `docs/` 폴더 내에 작성하여 제출해야 합니다.
    *   포함 내용: 데이터 분할 방식(시간 기반 8:1:1 등), 지표 계산식, 재현용 시드(`42`), 베이스라인 대비 개선율
